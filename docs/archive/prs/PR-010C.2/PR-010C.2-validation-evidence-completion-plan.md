# PR-010C.2 Validation Evidence Completion Plan

## 1. Purpose

本文件用于完成 PR-010C 的最后一轮验收证据补全，使当前状态从：

```text
PR-010C: CONDITIONAL PASS
```

升级为：

```text
PR-010C: PASS
```

当前 Contract 1.1.0 的架构方向、规范完整性和基础确定性已经基本成立：

- Contract version 为 `1.1.0`；
- Contract completeness report 为 `PASS`；
- fixture validation 为 `PASS`；
- geometry-first、mark separation、case-insensitive label normalization 和 fail-closed topology gate 已启用；
- candidate dataset 仍保持 `BLOCKED`；
- Production 未写入。

本阶段不再扩展 Contract 语义，也不修复 PR-010D candidate 数据。

本阶段只补齐三类验收证据：

1. 完整结构化 `issues[]`；
2. Contract 文档和三个 JSON Schema 的实体校验；
3. PASS、BLOCKED、REVIEW_REQUIRED 三类 fixture 的 deterministic rerun 证据。

## 4. Required Structured Issues Output

### 4.1 Candidate Validation Report

更新：

```text
pr010c-contract-validation-report.json
```

必须增加：

```json
{
  "candidateValidation": {
    "contractFailures": 34,
    "issues": []
  }
}
```

`issues.length` 必须与 Contract failure 的唯一 blocking issue 数量一致。

如果一个 record 同时触发多个独立 Contract invariant，可以产生多个 issue；但必须提供：

```text
uniqueFailureRecords
uniqueBlockingIssues
```

避免把 record count 和 issue count 混为一谈。

推荐结构：

```json
{
  "candidateValidation": {
    "uniqueFailureRecords": 34,
    "uniqueBlockingIssues": 42,
    "issues": []
  }
}
```

如果当前 `contractFailures = 34` 实际指 issue 数量，则必须明确命名：

```text
blockingIssueCount
```

禁止继续使用语义不清的 `contractFailures` 作为唯一计数。

---

### 4.2 Standard Issue Object

每个 issue 必须符合：

```json
{
  "issueId": "PR010C-ISSUE-000001",
  "code": "NEXT_QUESTION_LEAKAGE",
  "severity": "BLOCKING",
  "paperId": "0478-2023-ON-12-QP",
  "questionId": "0478-2023-ON-12-Q5",
  "childId": "0478-2023-ON-12-Q5-D",
  "ownerPath": ["d"],
  "message": "Child text contains spans owned by the next top-level question.",
  "failedInvariant": "Contract 4.9 Child Boundary Termination",
  "sourceSpanIds": ["span-1", "span-2"],
  "sourceEvidence": {
    "page": 5,
    "bbox": {
      "x0": 0,
      "y0": 0,
      "x1": 0,
      "y1": 0
    },
    "text": "The table contains descriptions about data transmission methods."
  },
  "candidateEvidence": {
    "questionText": "string",
    "marks": 1
  },
  "detectedBy": "canonicalQuestionBoundaryContract",
  "responsibleStage": "CONTRACT_VALIDATION",
  "publishBlocking": true
}
```

---

### 4.3 Required Fields

每个 blocking issue 必须至少包含：

```text
issueId
code
severity
paperId
questionId
childId or null
message
failedInvariant
sourceSpanIds
candidateEvidence
detectedBy
responsibleStage
publishBlocking
```

对于 source span 可用的 issue：

```text
sourceSpanIds.length > 0
```

对于无法恢复 source span 的 issue：

```json
{
  "sourceSpanIds": [],
  "code": "SOURCE_TRACE_INCOMPLETE"
}
```

不得伪造 bbox、page 或 source span。

缺失证据必须显式暴露，而不是填充假的零坐标。

---

### 4.4 Issue Code Registry Compliance

每个 issue code 必须来自 Contract 1.1.0 registry：

```text
CHILD_SPAN_OVERLAP
CHILD_SUCCESSOR_LEAKAGE
NEXT_QUESTION_LEAKAGE
MARK_ALLOCATION_IN_TEXT
STRUCTURAL_LABEL_IN_TEXT
UNOWNED_SEMANTIC_SPAN
AMBIGUOUS_SPAN_OWNERSHIP
TOPOLOGY_CHANGE_UNREVIEWED
SOURCE_TRACE_INCOMPLETE
INVALID_HIERARCHY_TRANSITION
DUPLICATE_SPAN_OWNER
EXCLUDED_MATERIAL_IN_TEXT
```

未知 code 必须使 PR-010C evidence validation 失败。

---

### 4.5 Issue Ordering

`issues[]` 必须按以下顺序稳定排序：

```text
paperId
questionId
childId, null first
source page
first sourceSpanId
code
issueId
```

同一输入重复运行不得出现排序变化。

---

### 6.1 JSON Schema Syntax Validation

三个 schema 必须：

- 可以被项目使用的 JSON Schema validator 加载；
- `$schema` 明确；
- `$id` 唯一；
- JSON 语法合法；
- 引用路径有效；
- 不存在 unresolved `$ref`。

---

### 6.2 Required Schema Assertions

#### Input Schema

必须要求：

```text
contractVersion
paper
sourceSpans
visualLines

ownershipAssignments
canonicalQuestion
topologyState
```

#### Output Schema

必须要求：

```text
contract
contractVersion
status
canonicalPublishable
summary
checks
issues
```

`status` enum：

```text
PASS
BLOCKED
REVIEW_REQUIRED
```

#### Issue Schema

必须要求：

```text
issueId
code
severity
paperId
questionId
childId
message
failedInvariant
sourceSpanIds
candidateEvidence
detectedBy
responsibleStage
publishBlocking
```

`severity` enum 至少包含：

```text
BLOCKING
WARNING
```

---

### 6.3 Positive and Negative Schema Fixtures

每个 schema 必须有：

- 至少一个 valid fixture；
- 至少两个 invalid fixtures。

Invalid examples：

- 缺少 `issueId`；
- 未知 issue code；
- `canonicalPublishable=true` 但 status 为 `BLOCKED`；
- `PASS` 但存在 blocking issue；
- duplicate span owner；
- source span 缺少唯一 ID。

Schema validation report 必须列出 fixture IDs 和结果。

预期：

```json

  "status": "PASS",

}
```

---

### 8.2 BLOCKED Fixture

构造至少两个 blocking issue：

```text
MARK_ALLOCATION_IN_TEXT

```

预期：

```json
{
  "status": "BLOCKED",
  "canonicalPublishable": false
}
```

必须验证多 issue 排序在两次运行中一致。

---

### 8.3 REVIEW_REQUIRED Fixture

构造：

```text
AMBIGUOUS_SPAN_OWNERSHIP
```

或：

```text
TOPOLOGY_CHANGE_UNREVIEWED
```

预期：

```json
{
  "status": "REVIEW_REQUIRED",
  "canonicalPublishable": false
}
```

---

### 8.4 Hash and Deep-Equal Evidence

每个 fixture 必须输出：

```json
{
  "fixtureId": "BLOCKED_MULTIPLE_ISSUES",
  "expectedStatus": "BLOCKED",
  "firstHash": "sha256:...",
  "secondHash": "sha256:...",
  "deepEqual": true,
  "comparedFields": [
    "visualLines",
    "ownershipAssignments",
    "issues",
    "issueCodes",
    "status",
    "canonicalPublishable",
    "checks"
  ]
}
```

`generatedAt` 必须排除。

Report 顶层：

```json
{
  "allFixturesDeterministic": true,
  "status": "PASS"
}
```

9. 34 个 failure 可以追溯到具体 record 和 issue；
10. pollution summary 与 issue counts 完成 reconciliation；
11. topology mismatch count 可以追溯到具体 paper IDs；
12. PASS fixture deterministic；
13. BLOCKED multi-issue fixture deterministic；
14. REVIEW_REQUIRED fixture deterministic；
15. issue ordering deterministic；
16. Production write 保持 `false`；
17. Stable IDs 没有变化；
18. Frontend 没有变化；
19. candidate status 继续保持真实的 `BLOCKED`；
20. 不得通过删除 issue、减少证据或放宽 Contract 获得 PASS。
