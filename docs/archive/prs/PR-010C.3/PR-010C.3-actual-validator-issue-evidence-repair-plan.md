# PR-010C.3 Actual Validator Issue Evidence Repair Plan

## 1. Purpose

本文件用于修复 PR-010C.2 中结构化 `issues[]` 证据不可信的问题，使 PR-010C 的 Contract validation evidence 真正来自实际 validator，而不是由 semantic diff、历史 `beforeQuestionText` 或目标计数拼装出来。

当前状态：

```text
PR-010C Contract Specification: PASS
PR-010C Schema Validation Report: CONDITIONAL PASS
PR-010C Determinism Evidence: PASS
PR-010C Structured Issues Evidence: FAIL
PR-010C Overall: CONDITIONAL PASS
```

当前阻塞原因不是 JSON 格式缺失，而是 issue 语义与证据不一致：

- `MARK_ALLOCATION_IN_TEXT` 的 candidate text 中并不存在 mark；
- `CHILD_SUCCESSOR_LEAKAGE` 没有 successor overlap 或 source span 证据；
- 34/34 issues 的 `sourceSpanIds=[]` 且 `sourceEvidence=null`；
- `TOPOLOGY_CHANGE_UNREVIEWED` 指向的 paper 不在 topology mismatch paper list；
- issue 排序没有遵守 Contract 规定；
- issue 顺序高度类似 semantic diff 前 34 条记录，无法证明它们来自真实 validator。

本阶段目标是：

```text
Actual Validator Output
+
Actual Candidate Evidence
+
Actual Source Trace
+
Actual Count Reconciliation
```

而不是继续把字段填满以后宣布通过。JSON 很擅长容纳证据，也同样擅长容纳装饰品，本阶段必须区分两者。

## 3. Core Rule

所有 candidate issue 必须满足：

```text
Issue code
=
Validator 对当前 candidate state 的真实判断
```

不得满足：

```text
Issue code
=
历史 Production 问题类型
```

也不得满足：

```text
Issue code
=
为了匹配 summary count 而分配的分类
```

`beforeQuestionText` 只能作为 historical comparison evidence：

```json
{
  "historicalEvidence": {
    "beforeQuestionText": "..."
  }
}
```

不能用于证明 candidate 当前仍违反 Contract。

## 4. Validator-Generated Issue Pipeline

### 4.1 Required Execution Path

必须确保 issue 的来源路径为：

```text
Candidate canonical record
        ↓
Canonical Question Boundary Contract validator
        ↓
Invariant check
        ↓
Issue factory
        ↓
Schema validation
        ↓
Canonical sort
        ↓
Validation report
```

禁止：

```text
Semantic diff
        ↓
Take first N records
        ↓
Assign issue codes
        ↓
Write report
```

---

### 4.2 Issue Provenance

每个 issue 必须包含：

```json
{
  "issueProvenance": {
    "validatorName": "canonicalQuestionBoundaryContract",
    "validatorVersion": "1.1.0",
    "checkName": "validateMarkAllocationSeparation",
    "inputRecordHash": "sha256:...",
    "generatedDirectlyByValidator": true
  }
}
```

`generatedDirectlyByValidator` 必须由 validator issue factory 设置，report serializer 不得后补。

## 5. Candidate-State Evidence Rules

### 5.1 MARK_ALLOCATION_IN_TEXT

只有在当前 candidate 的以下字段中实际存在 mark token 时才能触发：

```text
questionText
displayText
searchText
```

例如：

```json
{
  "questionText": "Describe sample resolution. [2]"
}
```

Issue evidence 必须指出：

```json
{
  "candidateEvidence": {
    "field": "questionText",
    "matchedText": "[2]",
    "matchStart": 28,
    "matchEnd": 31,
    "marks": 2
  }
}
```

以下情况不得触发：

```json
{
  "questionText": "Describe sample resolution.",
  "beforeQuestionText": "... [2] ..."
}
```

因为 mark 只存在于历史文本。

如果当前 candidate 没有 mark token，则该 issue 必须删除或重新分类。

---

### 5.2 CHILD_SUCCESSOR_LEAKAGE

只有在 current child 中检测到属于 successor 的具体 semantic fragment 时才能触发。

必须提供：

```json
{
  "candidateEvidence": {
    "currentChildText": "...",
    "leakedFragment": "...",
    "successorChildId": "...",
    "successorText": "..."
  }
}
```

并且至少包含一种 source evidence：

```text
shared sourceSpanId
overlapping source bbox
same source fragment assigned twice
boundary anchor after leaked fragment
```

如果只有：

```text
beforeQuestionText contains next question
```

而 candidate text 已经正确，则不能继续标记为 leakage。

---

### 5.3 NEXT_QUESTION_LEAKAGE

必须明确指出：

```text
current child
next top-level question ID
leaked fragment
source span ownership conflict
```

不得只根据历史 parent aggregate text 推断。

---

### 5.4 AMBIGUOUS_SPAN_OWNERSHIP

必须有真实 ambiguity 原因：

```text
two candidate owners
missing geometry
conflicting anchor hierarchy
insufficient boundary evidence
```

必须提供：

```json
{
  "candidateOwners": [
    {
      "ownerType": "CHILD_QUESTION",
      "ownerId": "..."
    },
    {
      "ownerType": "NEXT_TOP_LEVEL_QUESTION",
      "ownerId": "..."
    }
  ],
  "ambiguityReason": "..."
}
```

不能把“没有足够证据证明其他 issue”统一归为 ambiguity。

---

### 5.5 TOPOLOGY_CHANGE_UNREVIEWED

必须来自 topology reconciliation source：

```text
pr010e-reviewed-topology-decisions.json
or
topology mismatch detector output
```

必须满足：

```text
paperId ∈ topologyMismatchPaperIds
```

Issue evidence 至少包含：

```json
{
  "topologyEvidence": {
    "productionOnlyIds": [],
    "freshOnlyIds": [],
    "decision": "MANUAL_SOURCE_REVIEW_REQUIRED",
    "publishable": false
  }
}
```

如果 paper 不在 31 份 mismatch paper list 中，不得生成该 issue。

---

### 5.6 SOURCE_TRACE_INCOMPLETE

对于需要 source ownership 证据的 issue，如果：

```text
sourceSpanIds = []
sourceEvidence = null
```

必须执行以下二选一：

#### Option A

恢复 source trace，并保留原 issue code。

#### Option B

将 issue code 改为：

```text
SOURCE_TRACE_INCOMPLETE
```

并说明原始检查无法被证实。

不得继续断言：

```text
MARK_ALLOCATION_IN_TEXT
CHILD_SUCCESSOR_LEAKAGE
AMBIGUOUS_SPAN_OWNERSHIP
```

同时完全没有 source trace，除非该 invariant 可以仅凭 candidate field 本身严格证明。


## 8. Stable Issue ID

Issue ID 不应依赖数组位置：

错误：

```text
PR010C-ISSUE-000001
```

如果前面新增一条 issue，后续所有 ID 都会变化。

建议使用 deterministic key：

```text
sha256(
  contractVersion
  + paperId
  + questionId
  + childId
  + code
  + failedInvariant
  + normalizedEvidenceKey
)
```

输出：

```text
PR010C-ISSUE-<12-char-hash>
```

例如：

```text
PR010C-ISSUE-9F31A0C8B2D4
```

这样 rerun、sort 和 diff 才稳定。

如果项目必须保留序号 ID，则必须额外提供：

```text
stableIssueKey
```

用于跨运行关联。

## 9. Canonical Issue Ordering

所有 candidate issues 必须按以下字段排序：

```text
1. paperId ascending
2. questionId natural question-number order
3. childId natural hierarchy order, null first
4. source page ascending, missing last
5. first sourceSpanId lexical ascending
6. code lexical ascending
7. stableIssueKey lexical ascending
```

必须处理自然排序：

```text
Q2 < Q10
B-I < B-II < B-III
```

不得使用简单字符串排序把 `Q10` 放到 `Q2` 前面。
